# 重卡性能：大世界书 + 复杂前端美化

日期：2026-10-06
基准卡：「大渊习武录」（76 条世界书约 10.5 万字、27 条常驻；10 条启用的美化正则，单条模板 5–65K 字符，均无楼层深度限制；MVU + 3 个远程助手脚本）。
状态：A、D、E1–E3、G 已完成（G 未经真实模型实测）；E4 暂缓；F 已测量定位，待确认。

## 用户反馈

“对话稍微长一点就特别卡，整个 DSH 卡到白屏。”会话导出只有 18 轮，正文每轮 4–9KB。

## 已确认的问题

### 1. 发送关键路径被世界书筛选阻塞

点发送到正文请求发出的等待从 0.7s 涨到 37s，几乎全部是世界书筛选这次后台模型调用（6–32s）。

- 门槛过低：`>5 条 或 >2000 tokens` 即筛；中文按 1 token/字估算，一条人物资料就超门槛。只有 1 条候选的轮次也要等 6–11s，结果都是保留。
- 重复判断：卡要求每轮输出 GodView，里面反复出现势力名，扫描深度 2 每轮都命中；被排除的条目不冷却，连续 5 轮被同样排除。
- 缓存失效：筛选与结算交替运行在同一个后台 Session。
  - 筛选的 system 不带常驻世界书（`index.js` 中 `resolveCurrentWorldbook` 对筛选返回 `''`），第 0 个字就与结算不同。
  - 工具集按任务切换（结算 9 个、筛选 5 个），工具定义在可缓存前缀里。
  - 结算之间：任务消息开头是每轮变化的【当前变量快照】，其后约 6K 字不变的【变量结构】【变量更新规则】永远进不了缓存，cacheRead 卡在约 12K。
  - 结果：筛选输入 17–28K tokens，cacheRead 仅 2048。

本地计算不是瓶颈：离线复现到 200 楼，世界书投影、读写对话、任务准备均在 150ms 内。用户日志中筛选开始前 0.8s→6.3s 的本地等待离线未复现，怀疑服务端模板子进程排队，需端到端确认。

### 2. 前端：已加载楼层越多，内存与卡顿近平方增长（白屏主因）

用户会话正文循环拼成 20/50/100 楼，正式「导入聊天记录」后用无头 Chromium 测量（v2.5.0 · 9f775b1）：

| 楼层 | 阶段 | 长任务总计 / 最长 | iframe | 每个 iframe srcdoc | DOM 节点 | JS 堆 |
|---|---|---|---|---|---|---|
| 20 | 全部加载 | 0.7s / 0.32s | 7 | 5.2MB | 7.8k | 190MB |
| 50 | 全部加载 | 5.8s / 1.3s | 9 | 11.9MB | 17.9k | 459MB |
| 100 | 全部加载 | 42s / 5.9s | 13 | 23.6MB | 35k | 987MB |
| 100 | 滚动一遍 | 64s / 3.8s | | | | |

打开对话只挂最近约 13 楼，往上点「Load earlier」翻历史后才崩。整页 HTML 才进 iframe，其余片段内联进宿主页。

1. 每个 iframe 内联整局状态：`frame-document.js` 的 `state=JSON.stringify(helperContext)` 带上全部已加载消息，含每楼约 330KB 的 `pluginData.template_display` 与 formattingText，另有全部正则、世界书。iframe 大小随楼层线性、数量也随楼层增长。冷窗口 48 楼只在刚打开时有效。
2. `message-frame-lifecycle.js` 的 `createTavernHelperContextUpdate` 对每个 iframe、每条消息 `JSON.stringify` 比对并深拷贝。
3. `host-theme.js` 在 `document.head` 上的 MutationObserver 每插入一个 style 就 `getComputedStyle(body)`，强制整页样式重算（加载阶段 11.6s）；大 DOM 下宿主 `TurnNavigatorRail` 读滚动尺寸触发同步布局（滚动阶段 24.7s）。已加载楼层无虚拟化或离屏卸载。

## 方案

| 编号 | 改动 | 状态 |
|---|---|---|
| A | 筛选门槛改为“候选 >5 条 且 >3000 tokens”（初版 6000，后调为 3000，约 5000 中文字）；中文估算改为 0.6 token/字，8192 预算截断随之变准 | 已完成 `155ef3b1` |
| D | 被筛选排除的条目冷却 10 轮，期间直接排除不问模型 | 已完成 `a4dbbdfe` |
| E | 共享后台 Session 的请求前缀对所有任务完全一致，筛选复用结算缓存 | E3 `81d1277e`；E1、E2 见下次提交；E4 暂缓 |
| F | 前端：iframe 上下文减肥、主题观察器节流、比对缓存；远离视口释放已撤回 | F1/F2/F4 已完成 |
| G | 世界书筛选从“发送后”移到“上一轮回复结束后”预筛；发送时不再调用模型 | 已完成 |

### D：排除冷却

- 筛选模型排除的条目，记录排除时的剧情轮次；之后 10 轮内再次成为候选时直接排除，不进入筛选。
- 用户本轮输入直接命中该条目关键词时，不受冷却限制。
- 条目内容变化（渲染正文变化）时冷却失效。
- 冷却随剧情楼层：记录在 Chat 上，与已有 `worldBookReads` 冷却一样随回退/重新生成恢复。
- BM25 粗筛排除的条目不记冷却，只记模型判断。

### E：共享后台 Session 前缀一致

1. 筛选携带与结算相同的常驻世界书 system 段：沿用后台 Agent 上一次的投影，重启后首次由筛选自行投影。
2. 共享 Session 的工具集固定为所有任务工具的并集，按固定顺序注册；任务限制改在执行时检查，不属于本任务的工具调用返回错误；可用工具写进末尾任务协议。
3. 结算任务消息中，不变的【变量结构】【变量更新规则】排在每轮变化的【当前变量快照】之前。
4. 可选（暂缓）：筛选消息去掉与共享历史重复的 `recent`，约省 1.5K tokens；先看 1–3 的实测效果。

预计：筛选未缓存输入从 17–28K 降到约 5.5–10K tokens；结算再少约 3.4K。

### F：前端重卡

按收益/改动比排序：

1. F1 iframe 的 helperContext 去掉 `template_display`、`template_rendered`；有 `historyAccess` 时只内联最近 48 楼与本楼，其余为 stub，由 iframe 经已有的按需读取接口取用（`message-frame-lifecycle.js` 的 `tavernFrameHelperContext`，按宿主行对象缓存投影）。
2. F2 `host-theme` 观察器每帧最多读一次计算样式，不再每插入一个 style 就强制整页重算。
3. F3 远离视口释放：实现并复测后撤回。旧楼层卡片本就延迟挂载，100 楼全部加载后只有约 6 个消息帧，释放只减少 1 个、堆不降，反而多出约 2.7s 释放开销，并会重置旧楼层卡片的界面状态。
4. F4 增量比对先比引用，JSON 序列化按对象缓存，同一份上下文在多个 iframe 间只序列化一次。未改同步协议。

### G：回复结束后预筛

筛选是例外：本地判断不超门槛（≤5 条或 ≤3000 tokens）就直接用关键词结果，零请求。需要模型判断的候选主要由刚写完的回复带出，不必等玩家下一句输入。

- 时机：每轮回复结束、后台结算完成（或无需结算）后，本地按“刚写完的回复 + 上一句玩家输入”扫描下一轮候选。
  - 不超门槛：什么都不做。
  - 超门槛：在共享后台会话里跑一次筛选（与变量结算是两个独立任务，只是排在结算之后，复用同一份缓存）。
- 结果：模型排除的条目写入 `worldBookReads`（`kind: 'screened'`），之后 10 轮内直接排除；随回退/重新生成恢复；条目正文改变即失效；玩家输入直接点名时照常参与。
- 发送时：不再调用模型。关键词命中的候选去掉冷却中的排除项后，按 8192 预算截断注入。
- 玩家在预筛完成前点发送：取消预筛，不等；剧情已变化时预筛结果作废（任务提交检查 basedOn）。
- 预筛让路：其他后台任务（结算、候选、台账等）开始前先取消进行中的预筛；界面不把预筛显示为“后台结算中”，不禁用重新生成和候选按钮。
- 代价：预筛看不到玩家下一句输入；由“玩家点名照常参与”和预算截断兜底。

| 50 | 全部加载 / 滚动 | 5.8s → 4.0s / 11.3s → 6.2s | 11.9MB → 1.44MB | 459 → 318MB |

剩余瓶颈不在卡片：100 楼全部加载后正文 DOM 约 3.5 万节点（不是卡片），DSH 宿主 `TurnNavigatorRail` 在 activeTurn 变化时读取 scrollTop 触发同步布局（约 24s），其余为原生样式与布局（约 37s）。需要正文楼层虚拟化或限制同时挂载的楼数，属于宿主聊天列表。

### H：长历史楼层（不改 DSH 本体）

DSH 只渲染楼层外框；每楼正文与卡片由酒馆经 `conversation.chat.node` 插槽渲染，因此在酒馆侧收敛：

- 远楼占位：距最新楼层 ≥20 楼、离视口 2000px 外超过 2 秒的楼层，正文与卡片换成同高空 div；滚回附近恢复。导航条跳转仍准确。
- 卡片 slot 用该帧上次实测高度占位；retained 记录仍在时直接挂回，不再占位后重载。
- 卡片在视口上方变高变矮时补偿 scrollTop（浏览器已锚定则不补）。
- 预测量：未激活且没有记录高度的卡片，空闲时逐个在隐藏舞台加载、量高后关闭（最近的先量，卡片间隔 ≥400ms；挂载时只排队，不读布局）。

100 楼基准（全新浏览器上下文）：

| 指标 | 改前（F1/F2/F4 后） | 改后 |

| DOM 节点 | 34.8k | 15.1k |

遗留：卡片 retained 停放区里离屏卡片的 iframe 一直存活（约 19 个），滚动后 JS 堆增长约 45MB；这是保持卡片界面状态的既有设计，暂不处理。

### 已否决

- 筛选超时降级：筛选本身需 6–32s，几秒超时几乎必然触发，等于白跑。
- 筛选改独立短请求：丢掉后台结算积累的变量与已注入世界书；关键在复用缓存而不是独立。
- 筛选并进变量结算同一次请求：两者是独立任务，绑定后结算重试、无结算的卡都要另行兜底。
- 筛选做成后台 agent 自己调用的工具：让 agent 决定调工具本身就要一次模型请求，平时也得付出。
- 远离视口释放卡片 iframe（F3）：旧楼卡片本就延迟挂载，释放几乎不省内存，还会重置卡片界面状态。
