# 单局数据清单与存档导出/导入

日期：2026-10-06
状态：方案已确认（取舍按建议：带回退历史、默认带生图图片、删除时一并删除前台原生会话、只允许同版本或更新版本打开旧包）。第 1 步已完成。

## 目标

1. **逻辑整合**：一局游戏的数据分散在十几处，磁盘不动，用一份“单局数据清单”在代码里统一描述它们。
2. **导出存档 / 导入存档**：把一局打包带到另一台电脑，作为新的一局继续玩（含回退、重新生成）。
3. 顺带修正**删除游戏的残留**：现在删除只清存档和登记，日志、生图、后台会话等都留在磁盘上。

## 现状（排查结论）

一局的权威状态只有三处：

- `data/chats/<chatId>/`：酒馆存档，含全部历史 revision。回退、重新生成依赖 `timeline.checkpoints[].beforeRevision` 读历史 revision（最多 40 个）。
- DSH 前台原生会话 `sessions/<cwd 编码>/<sessionId>/session.v3.jsonl.zstd`：模型上下文与原生回合号，存档里的 `regeneratedDshTurns`、`nativeCommits`、checkpoint 都按它的回合号和 seq 对齐。
- `data/index.json` 与 `data/sessions.json` 里的登记。

其余按局存放的大多是日志、缓存或可重建的子会话；人物卡、世界书、预设、用户偏好在存档里已有快照（`cardDefinitionSnapshot`、`openingWorldbookSnapshot`、`runtimePresetSnapshot` 等）。仍直接读实时资源的：剧本模式的剧本、手机私聊、人物设计回写世界书、卡片更新检查、角色变量写卡。

不能整目录拷贝：

- 存档内部校验 `chat.id` 与目录名一致；生图记录的键由 chatId 参与哈希；`foregroundFrames` 的 frameId 含 chatId。
- 原生会话头部 `cwd` 是绝对路径，文件位置按它编码；宿主拒绝同一会话 id 出现在两个目录。换机器后只能用新 id、新 cwd 重建。
- 生图图片字节在 DSH 全局 `$DSH_HOME/attachments/`，不在酒馆目录里。

## 方案

### 1. 单局数据清单（`game-footprint.js`）

一个函数，输入 chatId，返回这一局在各处的全部数据，每项标注：

| 类别 | 内容 | 导出 | 删除 |
|---|---|---|---|
| 核心 | 存档（当前状态 + checkpoint 引用的历史 revision）、前台原生会话、两份登记 | 必带 | 清理 |
| 产物 | 生图记录 `scene-images/<sha(chatId)>/`、生图用世界书快照、引用的图片附件 | 可选（默认带） | 清理本局记录；附件仅在无其他引用时清理 |
| 依赖 | 人物卡文件、剧本（剧本模式）、无快照的老局世界书绑定 | 按需带 | 不清理（多局共享） |
| 子会话 | 当前与历史后台会话、生图、手机私聊、候选会话 | 不带（导入后重建） | 清理 |
| 日志与缓存 | `model-requests`、`model-request-sessions`、`worldbook-recalls`、`diagnostics/*`、`template-work`、`session-prefixes`、`chat-imports`、锁文件、宿主投影缓存 | 不带 | 清理 |

以后新增按局存放的数据，必须登记进清单；加一条测试：在临时目录里跑一局，扫描所有含该局 id（或其哈希）的路径，必须都在清单内。

### 2. 导出存档

对话顶部「导出」菜单新增「存档」，生成 `.dshsave`（ZIP）：

- `manifest.json`：格式版本、酒馆版本、原 chatId、卡名、轮数、导出时间、各部分校验和。
- `chat/current.json`：当前存档。
- `chat/revisions/<n>.json`：checkpoint 引用的历史 revision。人物卡与世界书快照每个 revision 都有一份（各约 4MB），按内容哈希只存一次，revision 里改为引用，避免 40 个 revision 撑到几百 MB。
- `session/foreground.jsonl`：前台原生会话的头部与全部事件，原样导出（含 seed 段和插件事件）。
- `card/`：人物卡原文件；剧本模式附带剧本；无快照的老局附带世界书。
- `scene-images/`（可选）：生图记录、生图世界书快照、图片附件。

前置条件：这一局空闲（无生成、无结算，复用分叉的检查），导出前先把原生会话落盘。

### 3. 导入存档

主页（或侧栏「新游戏」处）新增「导入存档」，导入为一局**新游戏**，不覆盖任何已有内容：

1. 校验格式版本：只接受同版本或更旧版本导出的包。
2. 人物卡：本机已有内容完全相同的卡就复用；没有就导入；同名不同内容另存为新卡。
3. 原生会话：服务端用新 sessionId、本机 cwd，以导出事件为 seed 调用 `agents.create`（与 DSH 分叉同一路径），并挂到酒馆工作区。
4. 存档：分配新 chatId；改写 id 相关字段（`sessionId`、frameId、生图键等）；按顺序把历史 revision 写成本机 revision，再回填各 checkpoint 的 `beforeRevision`（沿用“导入聊天记录”的做法）；后台会话设为 `needs-session`，首次结算时重建；清空 `forkedFrom`（导入后不能分叉到导出前更早的父局回合）。
5. 生图：重算记录键，写入附件，丢弃旧的生图会话绑定。
6. 登记并发布。导入过程用操作日志记录，中断后可续做或清理，不留半成品。

### 4. 删除游戏补齐清理

删除时按清单清理日志、缓存、子会话（含前台原生会话）和本局生图记录。DSH 仍在内存中持有的会话不删（否则会被写回），保持归档。生图图片附件在 DSH 全局附件库，可能被其他地方引用，暂不清理。

## 取舍（已确认）

1. **回退历史**：建议带上（导入后回退、重新生成照常可用）。代价是包变大、导入稍慢；大块快照已去重，预计一局在几 MB 到几十 MB。
2. **生图图片**：建议默认带，导出时可取消勾选。
3. **删除时前台原生会话**：现在只归档。建议改为随本局一起删除；如果你希望删除后仍能在 DSH 归档里找回，就保持归档。
4. **版本兼容**：只允许同版本或更新版本打开旧包。

## 分步实施

1. 单局数据清单 + 删除补齐清理 + 清单覆盖测试。
2. 导出存档。
3. 导入存档。
4. 端到端验证：真实一局（含 MVU、生图、回退过的轮次）导出 → 导入为新局 → 继续发送、回退、重新生成、分叉、删除，检查数据完整与无残留。
