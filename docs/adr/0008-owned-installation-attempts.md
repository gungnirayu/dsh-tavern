# 0008：安装更新由持有所有权的执行任务负责

状态：已实现；Windows 原生进程回收仍需 Windows 环境验证。

## 问题

更新涉及源码替换、依赖安装、Profile 配置、校验及启动。源码提交号相同不能证明这些步骤成功。界面请求结束、宿主重启、父进程退出和 PID 存活也不能分别证明安装停止或仍有进展。

原有 Profile 事务仅备份/恢复 package.json 和 cordis.patch.yml，不覆盖源码、node_modules、工作区、迁移数据或主题修改。因此不能把更新失败描述为完整回滚。

## 决定

保留现有安装流程和 Profile 事务，局部提取三个边界：

1. installation-state：每个 DSH_HOME 一个排他安装任务。UI 先保留 attemptId，独立更新器一次性接管，子安装步骤只加入同一任务。接管变更 generation，延迟启动回调不能覆盖新所有者。残留锁仅在两种情况下由下一次安装回收：所有者及 processes/ 下登记的全部进程均已退出（且锁已静默 1 分钟以上；所有者自己在退出前保留的锁标记 ownerDone，不再看所有者 PID、也不等静默期，因为 install.ps1 的所有者是用户仍开着的 PowerShell），或锁超过 1 小时无任何进展（长于整个受监督更新的 30 分钟上限）。否则关窗口、崩溃或 blocked 后，用户将被永久锁死且没有出口。
2. installation-process：有界、可取消的子进程执行。配置校验 60 秒、版本探测 30 秒、依赖命令 10 分钟、bootstrap Profile 步骤 20 分钟、整个 UI 更新 30 分钟。取消先关闭新子步骤入口，再等待所有所属执行链停止，最后才能恢复配置及释放安装锁。POSIX 使用进程组；Windows 使用挂起创建、加入 Job Object、恢复执行，以及 Job 活动进程计数归零确认。taskkill 仅是清理后备，不能单独证明孤儿进程已停止。CLI 的长期服务在 bootstrap 执行链清理和收据验证后，由独立更新器在安装 Job 外启动；否则 Windows Job 清理会误杀新服务。
3. installation-receipt：完整 Profile 验证、事务提交、运行时最终提交之后记录安装收据。收据绑定安装根、源码路径、宿主、attemptId 和配置/发布元数据指纹。更新器还必须确认 bootstrap 成功，才写 completed。新手动安装收据可以清除较早失败；同一次 bootstrap 在收据之后发生的失败不会被收据覆盖。

所有 update-status.json 读写统一使用已有持久文件提升协议，包括 Windows 延迟快照。状态更新在文件锁内校验任务/预期状态身份，旧异步检查和旧任务的终态不能覆盖新结果。

## 用户状态

- running：执行链仍被持有；显示阶段，允许受监督任务请求取消
- cancelling：已请求停止，仍保持排他，不能重试
- blocked：不能证明所有写入者已经停止，保持安装锁；绝不建议并行重装
- failed：已安全结束，但可能需要修复
- repair-required：没有新版本，但之前未完成安装；按钮明确为修复安装
- update-available：确认有后续构建
- completed：安装成功；Desktop 提示重启

旧更新器没有进程组登记，不能追溯证明孤儿进程已经退出，因此保守阻止自动重试。现代监督进程异常退出后，只在关闭的登记表和进程停止证据都有效时回收锁。损坏/缺失证据保留阻塞状态，需要人工确认执行链。

## 验证范围

针对性 Node 集成测试启动真实临时进程，覆盖挂起子/孙进程、忽略 TERM、取消、嵌套任务、父监督进程丢失、清理失败保持排他、跨实例抢占、旧任务迟到、超时后配置恢复、同版本修复和手动成功状态恢复。UI/API 使用 jsdom 和真实路由分发测试重复操作、迟到响应与网络超时。

这些进程夹具不是实际 DSH Desktop、真实 Windows 或浏览器端到端验证。Windows 的 Add-Type/Job Object 原生分支需在 Windows 执行相同测试及 Desktop 更新烟测；根因中的潜在宿主 Profile/端口争用仍未复现，不能据此宣称已经修复该未确定诱因。
